# Bronze package and consumer regression audit

2026-10-23. Read-only source audit of the installed `@shilo/bronze-ui` 0.1.0 CSS, `C:/Programming_Files/Shilocity/bronze-ui`, and the round-six consumer before the concurrent repair. This report records causes and recommendations; it does not certify the repaired UI or an operating-system native popup.

The reported problems primarily belong to the consumer integration. No package defect requiring a new release was established. Local package and installed release CSS are identical: tokens SHA-256 `5729ae3a6a99dade872d602c73129603e3e58e4a21c637a0e98c67847293eb7c`; components SHA-256 `167ab46204bdebfa949d39dc17d6eb61735766ace2effe57048aad8b4c8a7775`.

| Symptom | Source evidence | Ownership and repair |
| --- | --- | --- |
| Controls read as plain text | Consumer `styles.css` globally clears button border/background and often communicates pressed state with text color. `bronze.mjs` adds `.bu-btn` only to `.primary`; ordinary buttons never receive Bronze's bordered surface or selected border/fill/marker recipe. | Consumer. Give actions and choices a visible surface/border and persistent selected marker, using targeted classes or appropriately adapted package recipes. Navigation/display controls can retain their own treatment. |
| Equipment labels paint above a popup | Consumer `.item span` has `z-index:1`; item cards have no explicit stacking isolation. Consumer `.popover` has no explicit z-index. Bronze `.bu-floating` adds backdrop filtering, which creates a stacking context, but is a material recipe with no positioning/layer policy. | Consumer. Explicitly place popups above ordinary controls and contain item-label stacking inside each card. A larger opacity alone cannot fix an element painted above a popup. This source-level explanation follows the [MDN stacking-context rules](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Positioned_layout/Stacking_context); verify the real overlap with screenshots and hit testing after the repair. |
| White native select popup in dark appearance | Bronze tokens already set `color-scheme:dark`, switching to `light` on `:root[data-theme=light]`. Consumer imports those tokens and `applyTheme()` sets the root attribute. Creator selects receive `.bu-input`; playback selects retain a separate transparent consumer treatment. No explicit option foreground/background pair exists. | Missing scheme is not supported as the cause by source inspection. Check the actual select's computed scheme and open popup on the affected browser/OS. Explicit semantic foreground/background on native option/optgroup elements is a reasonable targeted hardening step where honored, but cannot promise identical platform chrome. |
| Oversized creator typography and collisions | Package default body size is 16px; `.bu-input` inherits typography. Consumer desktop rules explicitly set creator fields to 20px, editor tabs to 22px, presets to 17px and labels to 17px while fitting three fractional columns. The adapter explicitly preserves consumer geometry. | Consumer. Use approximately 16px form text with 14px labels and suitably sized targets; wrap or reflow control groups when content requires it. Do not preserve 20px merely to match the old geometry. Reduce columns before content collides; avoid clipping/fixed heights as a substitute for reflow. |

Bronze's documented contract supports this boundary. Its optional `base.css` changes document typography, and the consumer deliberately does not import it. The style guide specifies 16px UI text, 14px secondary text, at least 44px ordinary controls, opaque work fields, and native action popovers. The consumer uses ordinary absolutely positioned elements named `.popover`, whereas the package's native help popover uses the browser top layer. A CSS class name alone does not invoke native popover behavior. [MDN Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API).

There is no general WCAG requirement for 20px form text or for every button to have a border. W3C requires usable text enlargement to 200% and reflow for applicable content at 320 CSS pixels; visible boundaries can improve recognition, and necessary non-text indicators need sufficient contrast. A 16px form size is a design recommendation here, supported by the package's own default, not a claim of automatic accessibility compliance. Keep the larger hit target independently of font size. [W3C resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html), [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html), [target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

Native popup styling has a specific evidence limit. `color-scheme` is inherited and informs native form-control rendering; it does not prescribe a Bronze palette. Legacy option styling varies by browser/OS, with Chromium potentially honoring explicit text and background colors. Preserve native keyboard behavior and provide a matched foreground/background pair where customization is used. A computed root scheme alone does not prove the opened popup is readable. [MDN color-scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme), [option styling](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/option#styling_with_css), [select styling](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/select#styling_with_css).

Existing `verify-bronze.mjs` checks root scheme, token contrast, menu bounds and aggregate creator scroll width. Those checks do not assert popup paint order, actual option-menu rendering, every nested control's label fit, or persistent action affordance. Add focused verification for those observed regressions and review desktop, narrow portrait and shallow landscape. Geometry parity with an already problematic screen is not sufficient evidence of usable typography.

## Independent challenge of the repair

Source review of the in-progress repair found two remaining consumer issues, sent to the implementation owner for correction:

1. `creator.css`'s final `max-height:540px` rule selects two creator columns regardless of width/orientation. It overrides the narrow one-column rule on a 320 × 500 portrait viewport. With 40px horizontal workspace insets and a 24px column gap, each form column has at most 128px before form padding; the editor action row contains three icon buttons plus Enhance and cannot fit. Constrain the two-column shallow layout to sufficiently wide landscape, keeping a narrow portrait fallback. The browser verification matrix includes 320 × 568 and 568 × 320, so neither checks this crossing of conditions. This is a source-backed layout issue, not a new browser test result.
2. Consolidation removes the earlier mobile mirror-button width of 44px. The new `.compass .mirror` remains 26px wide on touch phones. This meets the 24px WCAG minimum dimension when its height is considered, but regresses the package's stronger documented 44 × 44 touch target contract and the former mobile treatment. Restore the coarse-pointer minimum while keeping the joined facing control readable.

The new creator stylesheet is a sensible ownership boundary: grid areas replace many conflicting screen-position overrides, and form typography no longer grows with viewport width. The guarded native `base-select` enhancement is also justified for the requested fully styled dropdown: it keeps ordinary select/option markup and browser semantics, with classic fallback. Source review found no reason to move these application layout repairs into the Bronze package or publish a package release. This review did not duplicate the separate browser verification run.

Both challenge findings are **resolved in source**. Re-reading `creator.css` confirmed the shallow two-column override now requires both `max-height:540px` and `min-width:541px`, preserving the narrow portrait column. A final `pointer:coarse` rule restores 44px mirror widths and uses a 6px compass gap. These findings are closed for source review; the separate browser reviewer owns the actual 320 × 500 and coarse-pointer fit checks.

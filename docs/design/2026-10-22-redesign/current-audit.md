# Current PixelDoll experience audit — 2026-10-22

This is a baseline of the **working app**, not a future design proposal. I used the normal local Vite server with the bundled offline demo in Playwright Chromium. The `pixeldoll.agentKey` switch was set to `off` before every page load, all `api.pixellab.ai` requests were blocked, and none occurred. No paid generation was attempted. The four viewport passes had no page errors or horizontal document overflow. Screenshots are under [`evidence/`](evidence/); layout measurements came from browser bounding boxes.

## Main design findings

1. **Creation starts inside the editor, behind a modal.** This makes the most important journey feel like opening a settings form. The demo character remains visibly dimmed behind the form, so attention is split between someone else's result and the user's choices. A fullscreen character-creation space could make the body prompt, choice feedback, and eventual review feel like one continuous experience. The real generation cost and time should remain visible at the commit point.
2. **The desktop default spends 38% of its width on permanent controls.** At 1440 × 900, the wardrobe is 248 px and inspector 300 px; the 640 px sprite canvas sits in an 892 px central area. The inspector starts with low-frequency controls such as layer order and hide rules exposed. These are valuable, but they make the default view read as production software rather than playful dressing. Start with the character and browsable equipment; reveal fine controls when an item is being adjusted.
3. **Phone portrait makes the character a small preview above a persistent control region.** At 390 × 844, the stage is 371 px high and the sprite canvas 256 × 256, while the lower panel is 421 px high. At 320 × 568, the sprite canvas drops to 128 × 128. The layout fits without horizontal overflow, but the character no longer owns the screen on a short phone. The colour view turns the lower half into dense swatch grids ([mobile colours](evidence/mobile-colours.png)).
4. **The same controls appear in several visual languages.** Desktop has a left list, right inspector tabs, and floating preview bar. Phone has slot chips, tiles, a fixed bottom tab bar, and the same preview bar. Landscape phone puts an editor column beside the stage. They are responsive, but the hierarchy changes by device: equipment is both a wardrobe list and inspector content on desktop, while colour controls attach to a chosen tile on phone. A redesign can use one simple mental model—character, category, choice, refine—across orientations.
5. **The demo promises immediate dress-up, then creation interrupts the next step.** The demo proves swappable gear quickly. Pressing `+` reveals the ownership/rig constraint only at that moment; after copying, the user sees another setup recommendation. Preserve the accurate distinction between a demo, an editable local copy, and a properly rigged generated body, but make the path legible before the interruption.
6. **Incomplete animation coverage is surfaced honestly but in technical prose.** The wizard hat visibly fits south/east/west, while north is empty and a warning explains it. Export also warns that missing frames stay empty. Keep these integrity signals; express them near the character and the final export decision, with clearer implications for a casual creator. ## Direction for the redesign

Use the character as the fixed focal point and turn the major actions into a short sequence: **choose/create a body → dress it → refine a selected part → preview motion → export**. The first-run/create path deserves a fullscreen setting with fewer simultaneously visible controls. During dressing, present equipment as visual choices close to the character; move material ramps, layer order, fit/coverage, rig details, and job activity into contextual refinement surfaces. Preserve all technical controls and integrity warnings, but let users reach them when the decision is relevant. On phones, give the character enough room to remain recognizable while category and item trays move in and out. The current clean dark palette, crisp pixel scaling, direct manipulation, and instant offline demo are strong foundations.

This audit distinguishes the current implementation from the separate research/proposals in `docs/research/character-creator-design-research-2026-10-22.md` and `docs/testing/create-character-review-2026-10-22.md`. Those documents were not used as proof of current behavior.

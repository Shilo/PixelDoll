# App bars final adversarial review

The shared header fixes the placement problem, and the three main bars keep Full screen and More at matching positions. The remaining release blockers are draft loss under nested surfaces and end-to-end scenarios that still target the retired UI.

Reviewed the working tree against base `f68530198`, including the new components, the staged deletion, the prior review, and the approved plan with its As built exceptions. Used T3 preview against the existing server at port 5241 and an incognito copy of the demo for editable surfaces. T3 reported “The browser is not producing screenshot frames” on both screenshot attempts. The visual findings below use live DOM, computed layout and focus, and CSS inspection. Pixel-level appearance, touch and the software keyboard remain unverified.

## Findings

### P1. Closing a child sheet silently discards the New character draft

**Observed at 1280 × 800, dark.** Type in Details, then open More → Settings. Back to New character retains the text, and the creator's own Back asks to discard it. Go to Settings again and click its X. Both screens close immediately, and the draft is cleared. Connect and Activity use the same close assignment. This also clears the explicitly saved draft when the user cancels a Connect opened by Create or Enhance, breaking the retained-input expectations in the creator tests. **Fix:** Route exits that would leave both screens through a guard that includes the suspended creator's dirty state. Preserve the input on cancellation of a connection prerequisite and cancel only its pending action. **Counterargument:** The implementation explicitly says a child X leaves both. That determines the destination, and the approved exit rule still requires confirmation before losing typed input. Closing a pending connection previously kept the text. ### P2. Browser Back can act on the sheet behind a foreground alert

**Source verified.** Sheet special-cases its own Discard state, and browser Back dismissed that alert while preserving the creator text in preview. Other instances of ConfirmDialog never claim the exit. For example, with an unsaved Directions change and its Save confirmation open, the parent is dirty and unlocked until saving starts. Browser Back calls the parent's close request, which can put Discard changes on top of the save alert. In Settings, opening Reset sets the parent lock even before saving, so browser Back does nothing while Escape can cancel the alert. **Fix:** Resolve browser Back against the foremost modal and let an idle alert call its safe action. Keep the navigation lock while that alert is committing. **Counterargument:** A single active sheet normally suffices and Discard itself works now. These are two real stacked-dialog paths with different outcomes. **Source verified.** ConfirmDialog installs the backdrop action on every alert and dismisses unless busy.

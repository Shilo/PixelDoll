# Project folder shared runtime research

**Prioritize shared-runtime work without waiting for a user report.** Unity 6000.4.0f1 rejected the generated C# of this branch even with distinct characters (a missing brace that main had already fixed in 21c4cdddf). Repairing that syntax in disposable copies exposed an independent Unity assembly-name conflict when the same export ID was present twice. GDevelop also collided on an equal ID when two exports were merged into one scene. Godot and Phaser ran both sibling exports in every tested case. The project-folder change should put reusable runtime code and integration docs in a PixelDoll-owned directory under the picked parent, with each character pinned to a runtime version. ZIPs should continue carrying everything they need.

## Test setup

- Current commit `9d06cf07e4585d66ab67ac5db59dbdbca2ca2dda` and historical commit `23281e1af` were built offline under Node v25.0.0. Every sample was freshly built from the bundled s2 fixture through the production `buildExport` with `filesOnly: true`, a fixed timestamp, and the walk selected for RPG Maker. A and B share the stored body and item IDs on purpose. They have different export IDs, names, and active outfits. A wears Adventurer and B uses Base only. This exercises distinct asset identity with overlapping layer IDs. There were no PixelLab calls, actual directory picker sessions, or changes to tracked files.
- Each format has three separate temporary projects. `distinct` has current A and current B, `duplicate` has two separately built, byte-identical current A exports, and `mixed` has current A and historical B. Every case puts its two raw exports in sibling directories `a/` and `b/`. Unity places these under `Assets/`. For GDevelop and RPG Maker the runtime tests explicitly apply the asset-integration steps required by those formats. The historical source produces different Godot, Unity, Phaser, and GDevelop runtime bytes, plus different docs. Aseprite, generic PNGs and RPG Maker character PNGs had no artwork byte changes for the same input across these revisions.
- Test output lives under `%TEMP%/pixeldoll-shared-855d14b9/matrix/` for this run. `matrix.json` records counts, per-format historical differences and data checks. Paths below are relative to one scenario root unless otherwise stated. Each current export included `AGENTS.md`, `CLAUDE.md` and `docs/<format>.md` and repeated those per character. The historical revision predates these files.
- The focused Vitest command passed 20 files, with 204 passing tests and 4 expected failures. `GODOT_BIN` was set to the 4.7.1 console executable. The opt-in Godot test imported and ran its own project and exported and ran a PCK. The separate project-folder tests cover the browser-free trust and publish behavior independently of this export matrix.

### Godot

All six imports/runs exited 0 with no `ERROR:` or `SCRIPT ERROR`. Each `res://<side>/godot/Paperdoll.tscn` had the script at `res://<side>/godot/paperdoll.gd` and the active walk texture at `res://<side>/layers/body/base/main/walk.png`. This directly verifies path isolation for the embedded GDScript and SpriteFrames, including an identical scene node name on two instances. Source inspection confirms no `class_name` on the generated controller. The test used player instantiation and playback lookup. Cross-version action layering and custom project-level global declarations were outside this test.

### Unity

- The repository's `verify-unity-export.mjs` failed before running its playback or render methods. Unity reported `Assets\LayeredTiming\unity\Runtime\Paperdoll.cs(96,25): error CS1513: } expected` and the same diagnostic at `Assets\RenderNative\unity\Runtime\Paperdoll.cs(96,25)` and `Assets\RenderFractional\unity\Runtime\Paperdoll.cs(96,25)`. The matrix reproduced it at `Assets\a\unity\Runtime\Paperdoll.cs(96,25)` and `Assets\b\unity\Runtime\Paperdoll.cs(96,25)` for distinct current exports, and on A alone for the mixed case. In the current template, `SetDirection` lacks its closing brace immediately before `public bool IsActionPlaying`. Git blame points to merge `6a3b0b49f` at the affected boundary.
- In both the raw and brace-repaired duplicate projects, Unity exited 1 with `Assembly with name 'PixelDoll.Character_9593a16718783599.Editor' already exists` for `Assets/a/unity/Editor/PixelDoll.Editor.asmdef` and `Assets/b/unity/Editor/PixelDoll.Editor.asmdef`. It also reported `Assembly with name 'PixelDoll.Character_9593a16718783599.Runtime' already exists` for `Assets/a/unity/Runtime/PixelDoll.Runtime.asmdef` and `Assets/b/unity/Runtime/PixelDoll.Runtime.asmdef`. A different directory alone provides no Unity assembly isolation. The repaired distinct and mixed matrices both compiled with exit 0.
- Batch execution of the actual importer after the one-brace repair produced `Assets/a/unity/Generated/adventurer-a.prefab` and `Assets/b/unity/Generated/adventurer-b.prefab` in both the distinct and mixed cases. Each prefab carried a paper-doll component from its own generated runtime namespace. Playback and rendered-pixel verification of the repaired control were outside this test.
- Source inspection shows the Editor importer is also keyed by export ID. Its postprocessor finds `*/unity/pixeldoll_unity.json`, checks that ID and writes under the matching export's own `unity/Generated/`. This importer can become common code if it reads and validates data per path. Generated prefab and clip identities and the existing Unity script/assembly type identity require an explicit migration design. Moving a source script to a package alone cannot preserve references in an existing game.

### Phaser

All nine sibling combinations ran without a browser page error. The two imported `phaser/PaperdollContainer.js` modules had different module/class identities and both operated on the same game's texture and animation managers. In the identical-ID case, the actual keys were `pd:["http://phaser-siblings.invalid/a/","base","main","walk"]` and `pd:["http://phaser-siblings.invalid/b/","base","main","walk"]`. The corresponding animation keys used the same separate URL prefixes and `"walk","south"`. Each doll entered its own registered animation. The repository Phaser verifier independently completed its existing Canvas and WebGL checks on all three versions. The sibling checks used Canvas and loaded both characters sequentially. They did not exercise two module implementations racing to load the same exact character URL.

### GDevelop

- The repository verifier ran the official editor core, web exporter and GDJS/PIXI with an independent pair of fixtures. The first attempt used a partial old extraction that lacked `resources/GDJS/Runtime/gd.js` and other includes and timed out waiting for the scene. Extracting `resources/GDJS` from the cached official portable ZIP fixed the harness setup. The verifier then passed timing, State playback, origins, tuck, depth, palettes, independent dolls, stop, unequip and destruction.
- The matrix merged the sibling exports' objects, resources and inline events into one `Paperdoll` scene, following the repository harness's merge method and pointing the resources to the two sibling trees. Distinct and mixed IDs ran, started both walks in one real native runtime, and registered independent libraries at `runtimeScene.PixelDoll_PD_9593a16718783599` and `runtimeScene.PixelDoll_PD_95939e6718783080`. GDevelop logged `Platform "GDevelop JS platform" is unknown.`, `Child uiSettings not found in SerializerElement::GetChild` and `Child objectsGroups not found in SerializerElement::GetChild` during deserialization. The engine still exported and loaded those projects without page exceptions or missing web files.
- Same ID produced 14 duplicate object names, 784 duplicate resource names and the same scene key. The raw merge in `duplicate/duplicate-merged.json` failed in the native web exporter with `ENOENT: no such file or directory, copyfile '<matrix>/gdevelop/duplicate/9593a16718783599_0_0_0_0_0.png' -> '<web>/duplicate/html/9593a16718783599_0_0_0_0_02.png'`. This is the result of the scripted raw merge, not a claim about the GUI's manual object-copy conflict dialog. After removing repeated object and resource definitions while keeping both generated events, the exported scene ran with one shared library and one doll. Source inspection shows the second event skips its initialization and still calls the same library's update loop. A twice-per-frame timing effect was not measured.
- Merely placing two independent `gdevelop/game.json` projects in sibling folders does not import either into the other. For a real shared controller, separate common code from the embedded per-character manifest and object bindings. `gdevelop/Paperdoll.js` is a readable copy and the current generated event already embeds the code. Removing only that copy would save disk but leave each imported event carrying the runtime.

### Data formats

- **PNG + JSON.** Both manifests at `a/manifest.json` and `b/manifest.json` refer to paths such as `layers/body/base/main/walk.png`. The offline check resolved every reference relative to its manifest and decoded 28 PNGs per export without errors. There is no format-specific engine. A third-party integration can still create its own global collisions if it keys both characters by export ID or flattens the sibling roots. No third-party integration was run.
- **Aseprite.** A single stock CLI process received `a/aseprite/adventurer-a.aseprite` and `b/aseprite/adventurer-a.aseprite` (duplicate) or `b/aseprite/adventurer-b.aseprite` (other cases) and saved 38 PNGs per document. On this workstation the installed PixelLab extension emitted `%APPDATA%\Aseprite\extensions\pixellab\handle-pose.lua:58: attempt to index a nil value (local 'dlg')`, also with a `./handle-pose.lua` spelling, even for `--version`. Batch exited 0 and returned all frames. This is an installed extension startup issue, separate from the exported data. Initial harness lookup expected `a.png` and raised `ENOENT`. The successful run checked the actual numbered frame files.
- **RPG Maker Standard.** The installed MV `1.6.1` game runtime ran in its bundled NW.js `0.29.0`. In one disposable project, MV's `ImageManager` and `Sprite_Character` loaded both primary character sheets for each of three pairs under `www/img/characters/`. The probe added scenario suffixes so all six sheets could be loaded in one process. A measured 54×50 px per frame and B measured 24×46 px. The duplicate was two separate 54×50 sprites after the second filename gained a `-relink` suffix. MV returned identical cache keys for the original `img/characters/$adventurer-a.png` names. Different revisions or outfits with the same export filename cannot both occupy that path without a rename. The other sheets were decoded offline. The installed runtime passed the image-loading and sprite-layout checks. RPG Maker's editor UI and map gameplay were outside the probe. No scripts or runtime packages are emitted for this format.
- **RPG Maker XP.** Native XP and Pokémon Essentials execution were unavailable. In all six exports the PNGs decoded and matched the expected 4×4 geometry without the Standard `$` prefix. Source and file inspection show the analogous path collision on `Graphics/Characters/adventurer-a.png` when flattening. The Windows search found RPG Maker MV and a VX Ace workshop project directory, but no XP editor executable. The RPG Maker source-level results cannot establish behavior in MZ, VX, VX Ace, XP or Pokémon Essentials.

## How engines distribute common code

- **Godot** uses project-local `addons/<plugin>/` and `plugin.cfg` for editor plugins. A plain runtime GDScript can be shared through a resource path without an editor plugin. Relative resource references keep the character tree portable when the picked folder is a game subfolder. Keep per-character scenes, libraries and texture paths separate, and avoid a global `class_name` or autoload unless the integration needs one. [Godot editor plugin layout](https://docs.godotengine.org/en/stable/tutorials/plugins/editor/making_plugins.html)
- **Unity** uses UPM package manifests with a package name, version and typically `Runtime/`, `Editor/`, `Documentation~/` and distinct assembly definitions. Unity compiles scripts under `Assets/` automatically, so retaining two source trees with the same assembly names breaks even if only one is referenced. A stable installed package identity and preserved Unity metadata are important for component references. The browser picker may grant only a folder under `Assets/`, so package installation outside that subtree requires user action and access. [Unity custom packages](https://docs.unity3d.com/6000.0/Documentation/Manual/CustomPackages.html) · [Assembly definitions](https://docs.unity3d.com/6000.0/Documentation/Manual/assembly-definition-files.html) · [Embedded packages](https://docs.unity3d.com/6000.0/Documentation/Manual/upm-embed.html)
- **Phaser** fits an ES module shared by import URL or a versioned npm package imported by package name or export entry. A folder publish can supply the dependency-free ES module directly. Leave the user's `package.json`, lockfile and bundler setup under their control. A package release later could simplify use across multiple projects. [Node ES module resolution and URL caching](https://nodejs.org/api/esm.html) · [npm package fields](https://docs.npmjs.com/cli/v11/configuring-npm/package-json)
- **GDevelop** uses project extensions for reusable event functions, behaviors and custom objects. A native extension can be installed or imported once while each character supplies its own resource paths, sprite bindings and placement. An extension's stable function and behavior identifiers still need project-wide ownership and a deliberate upgrade. Sibling JS files alone will not refactor the existing inline-event integration. [GDevelop extensions](https://wiki.gdevelop.io/gdevelop5/extensions/) · [Create an extension](https://wiki.gdevelop.io/gdevelop5/extensions/create/)

## Layout decision

| Option                                             | Benefits                                                                                                                                                     | Costs and conflicts                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Reserved, versioned shared directory**        | One common runtime and guide per engine and compatible version. Supports separate character data, pinned dependencies and one destination-wide trust record. | Requires small format-specific adapters and shared ownership. Unity needs one active package or compiler-visible tree. GDevelop needs one installed extension plus separate resource bindings.                                                                                                        |
| **B. Runtime and docs loose in the picked parent** | Leaves character paths simple and immediately visible.                                                                                                       | Can collide with the game's existing `AGENTS.md`, `CLAUDE.md`, `docs/` and source conventions. A single mutable path allows old and new automatic publishers to fight. Root-level agent files can affect unrelated game work. Requires the same ownership work while increasing collision scope.      |
| **C. Namespace each character runtime**            | Keeps self-contained exports easy to move and can allow several copies if the namespace includes a destination identity.                                     | Current ID-based namespaces already fail for relinked copies. A folder-scoped salt would still repeat runtime and guides, force a new type identity on relink, and make future runtime fixes repeat across characters. Keep namespacing for character assets and instances where the engine needs it. |
| **D. Keep sibling self-contained exports**         | Least implementation effort and already works in tested Godot and Phaser configurations.                                                                     | Leaves the native Unity and GDevelop same-ID failures, extra source to review and uneven upgrades. Suitable for standalone ZIP downloads.                                                                                                                                                             |

Choose A while keeping B's intended structure of one common home and sibling characters. Example destinations in the UI are **Character** `GameAssets/adventurer-a` and **Shared runtime** `GameAssets/_PixelDoll/phaser/v1-<digest>`. The default setting can keep the existing character path prominent and show the shared location as a secondary line where the engine uses one. Shared conflict review and copy-path actions should show the exact actual path, e.g. `GameAssets/_PixelDoll/phaser/v1-<digest>/PaperdollContainer.js`. Settings currently constructs conflict paths by prefixing every path with the character subfolder, so a shared conflict needs its own destination scope. For an external Unity or GDevelop install, display the release path and the engine's install step. For Aseprite, PNG + JSON and RPG Maker, the character path suffices, with shared integration docs optional. Keep character-specific quickstart commands and resource locations with the character or derive them from a single shared guide.

## Safety, upgrades and rollout

1. **Fix and prove the Unity regression now, about 0.5–1 day.** Restore the missing brace and run the existing stock Unity verifier with its playback checks on untouched generated code. Document the duplicate-ID limitation immediately for existing exports. Add an explicit duplicate same-destination test before any new shared layout. No report from a user is needed to act on a reproduced compile failure.
2. **Extract the common assets and implement the folder contract, about 3–5 engineering days.** Make project-folder output an explicit profile of the builders. Emit a versioned runtime bundle, character data and a small version reference. Keep ZIP output self-contained. Begin with Phaser and Godot and prove both share a single module/script and continue to load character-relative data. Route generic integration guides under `_PixelDoll/docs/` only if there is a clear benefit. Do not emit generic project-wide agent instructions into the game's own root. Treat runtime identity as an API version plus a digest calculated from emitted runtime bytes. Publishing a second character against identical bytes should reuse that version without rewriting it, and an older tab should only be able to publish against its pinned version if compatible with the destination policy.
3. **Give the shared folder its own browser trust record and serialization, about 2–4 days, partially overlapping step 2.** Today `links.ts` tracks metadata by character and files by link and relative path, and the Studio locks by lowercased subfolder name. Two character locks do not protect a shared file. Reuse the permission-bearing handles and match the actual parent via `isSameEntry` during a global registry lock. Store one trusted per-parent/engine runtime record in IndexedDB, include a layout generation, and serialize all runtime work for that stable destination under Web Locks. A folder marker can describe version and compatibility, but cannot grant trust. When locking or safe destination identity is unavailable, keep character writes isolated and pause shared changes. Different origins, browser profiles or external programs cannot share these locks.
4. **Publish complete versions before switching any character, and keep upgrades deliberate.** For Game A's pinned dependency, version directories are create-only during ordinary publish. Check every file against the expected digest, record every write as pending until its hash is committed, then record the complete version before publishing a character reference. A partial write never becomes a dependency. Already-matching foreign bytes can be read for reuse and remain user-owned unless explicitly adopted. If a known file is missing or changed, show its exact state and require approval of the current hash or deletion sentinel before touching it. If preserving a modified runtime would break the contract, keep publishing blocked for dependent characters until the user chooses a compatible runtime. Preserve existing publisher ordering and stage-time hash checks. The File System Access API has no compare-and-swap at final close, so the existing last-check/close race remains. Never auto-delete old files, sidecars or directories.
5. **Use one Unity active install and one GDevelop extension identity, about 4–8 days including native verification.** A Unity-compatible design should retain a stable assembly, script identity and importer, read character manifests by path, and have one compiled runtime under any given project. Versioned payloads can be staged outside Unity import roots or in a file format Unity does not compile. A newer compatible install should support older character data. Switch an incompatible version only in an explicit user-reviewed project-wide update with a minimum compatible writer/version check under the same lock, never by alternating mutable writes from character auto-publish. Keep engine-generated `.meta`, prefabs and user script changes safe. For GDevelop, use a single extension registration, then test two distinct characters, repeat instances of one character and two versions of the data format in a merged scene. Record a clear identity rule for intentionally linking one character twice.
6. **Offer an explicit transition for existing projects, plus 2–3 days for UI and browser safety coverage.** No automatic relocation or cleanup. Existing exports may already be referenced by scenes or compiled by Unity. Let users preview new character and shared paths and remove or move obsolete code themselves in their engine. Lock a fresh layout namespace and avoid reusing any destination an old app tab can still write. Require users to reload/unlink the old publisher before changing a live link. Keep the old tree intact unless the user edits it in their project. Cover concurrent publishes, older tabs, interrupted writes, unlink while pending, edited and deleted dependencies, identity collisions and source-bundle update. Shared code should be scheduled as product work now. Its rollout can be phased by engine.

The planner proof uses current `planPublish` directly. It confirms that matching bytes without a record are foreign, a fresh per-link record can treat a deleted shared path as new, and a shared record alone allows an older writer to replace exact v2 bytes with v1. It also confirms exact-hash approval and pending/deleted behavior. These outcomes are why the shared code needs both destination-scoped trust and an immutable version or explicitly locked upgrade policy. [Planner repro](./trust-model.mjs)

## Reproduce

Run from the repository root in PowerShell. The harnesses write only to a fresh temp directory. The Unity control adds one brace to the current generated C# in a disposable project.

```powershell
$research = 'docs/research/2026-11-27-project-folder-shared-runtime'
$scratch = Join-Path $env:TEMP ('pixeldoll-shared-' + [guid]::NewGuid().ToString('N'))
$older = Join-Path $scratch 'older'
$matrix = Join-Path $scratch 'matrix'
New-Item -ItemType Directory -Path $older | Out-Null
git archive --format=tar --output=(Join-Path $scratch 'older.tar') 23281e1af app/src
tar -xf (Join-Path $scratch 'older.tar') -C $older
node --experimental-transform-types "$research/build-matrix.mjs" $matrix $older
node --experimental-transform-types "$research/trust-model.mjs"
node "$research/native-projects.mjs" $matrix godot $godotConsoleExe
node "$research/native-projects.mjs" $matrix unity $unityEditorExe
node "$research/native-projects.mjs" $matrix unity-import $unityEditorExe
node "$research/native-projects.mjs" $matrix aseprite $asepriteExe
node "$research/rpg-maker-mv.mjs" $matrix $rpgMakerMvDirectory
node "$research/phaser-siblings.mjs" $matrix $phaserVendorDirectory
node "$research/gdevelop-siblings.mjs" $matrix $gdevelopDirectory $libGDCjs
```

Pass the Phaser verifier's temporary `--vendor-dir` to the sibling script. Pass a full GDevelop `resources/GDJS` from the 5.6.285 portable ZIP and `libGD.cjs` with its accompanying `libGD.wasm`. For the stock Godot, Unity and Phaser commands, run from `app/` as documented. For the stock GDevelop verifier, run its absolute script path from a temporary working directory because it writes relative to the current working directory. Use a fresh matrix when repeating the Unity compile checks.

## Conditioning separates identity, pose and finishing

Pixelmon's character path draws a standing reference, then paints each requested pose beside a reference on a two-cell canvas. Only the new cell is editable. Its edit rectangle follows the skeleton envelope with room for clothing and weapons. Each facing gets its own standing reference, generated beside the nearest available facing. A back-facing target gets a negative prompt for face, eyes, nose and mouth. Its turnaround path instead renders a model's per-view depth in Blender, then supplies that depth and a common image reference to SDXL. The same seed is used across those views. These are distinct controls for geometry and appearance. Neither route emits independent, frozen-body equipment layers. [Two-cell animation and facing references](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/sprites.py) · [Turnaround depth and reference inputs](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/turnaround.py)

Sprite Foundry also has distinct source routes. A turnaround LoRA draws front, side and back together on a wide canvas. An iterative route refines a front image with low-denoise img2img and rotates through IPAdapter references. Its morphology route uses body-class depth primitives and class-specific ControlNet strengths and timing. The primitives constrain the subject's mass and orientation, while the reference guides appearance. A shared seed alone does not enforce frame registration or item ownership. These are whole-character generation routes. [Turnaround workflow](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/pipeline/foundry_gen_turnaround.py) · [Iterative reference route](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/pipeline/foundry_gen_iterative.py) · [Morphology controls](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/pipeline/foundry_gen_morph.py)

PixelDoll already has a stronger geometry contract for equipment. It owns each target body bitmap and pose, and the matched live trial uses the same facing's approved design. The transferable experiment is to change one supplied reference or conditioning image while holding targets and artwork identity fixed. Copying the external diffusion graph would add a model stack and lose the current PixelLab interface boundary. Raw Skeleton v3's stored joints and its documented depth hints remain the supported geometry controls here. ## Palette metric comparison on retained equipment

Pixelmon's general palette node offers OKLab and a red-weighted RGB approximation called redmean. Its dedicated sprite animation path uses redmean to map every visible pixel to a standing palette. Alpha is thresholded at 128. Its palette extraction keeps the exact colors of a small palette and uses median cut for denser pictures. All 59 standing views in this replay had at most 23 distinct visible RGB values, so they qualify for its exact palette path. [Palette metrics and cleanup](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/custom_nodes/pixelart_palette/nodes.py) · [Animation palette lock](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/sprites.py) · [Exact-palette selection](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/colors.py)

The replay uses the same 59 non-reference standing views, 17 item cases, and six signed RGB offsets as the earlier dye study. Each original standing pixel is the exact target. The offsets are ±(8, −4, 2), ±(2, 8, −4), and ±(−4, 2, 8), with channel clipping. The stronger arm multiplies them by 2.5. The production `autoRamps` result provides reproducible ownership labels, and each facing supplies its own full standing palette, including unowned colors. These labels are derived from the artwork and are not independent artist annotations. Every strength contains 138,822 owned-pixel observations and 13,230 unowned observations. The observations are correlated perturbations of fixed inputs, so these rates do not estimate PixelLab's real error frequency. [Existing benchmark](../testing/bench.md) · [Production matcher](../../app/src/lib/dress/item-palette.ts)

Unbound means the production matcher leaves a perturbed color outside the standing palette. The three nearest-color methods always return a standing color. The comparison includes colors that perturb onto an already present but incorrect standing shade, which the production policy deliberately preserves. Equal-distance ties follow candidate order. The source OKLab matrices and redmean weights were implemented equivalently in pinned Node, rather than executing their Python functions. The implementation uses double-precision arithmetic and the source's color-space linearization. The production arm invokes `standingDyeMatcher` directly.

Redmean has a small exact-recovery advantage over Euclidean nearest in this channel-offset test. OKLab has more incorrect assignments and more unowned-to-owned assignments in the mild arm. This does not rank their perceptual appearance on arbitrary images. It shows why a perceptually motivated metric cannot be adopted as a safer material classifier without a corresponding test. Full palette membership also cannot prove that a buckle, hem or emblem retained its intended shade or location. The measured bounded default still trades correction coverage for fewer unsafe assignments. Test any alternative on the same paid outputs and material boundaries before changing it.

## Color-island cleanup destroys some native details

The general Pixelmon finalizer performs palette matching and then, by default with dithering off, recolors every eight-connected island of at most two identical-color pixels to the most common neighboring color. It repeats for up to two passes. A small highlight inside an otherwise large, connected item is therefore eligible. This differs from removing a detached alpha component. Pixelmon's dedicated small-sprite path has its own block-dominant pixel reduction and explicitly records that the general finalizer had removed thin legs and staffs. The source already treats processing scale as consequential. [Color-island cleanup](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/custom_nodes/pixelart_palette/nodes.py) · [Dedicated native-cell processing](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/sprites.py)

An equivalent two-pass replay on PixelDoll's 59 retained isolated standing layers changed 4,291 of 25,342 visible RGB pixels, or 16.9%. It mapped 1,367 visible pixels to black. For this adaptation test, transparent RGB was the stored zero value and the original alpha mask was held fixed. Thus the black count describes recoloring, not automatic alpha removal. The replay does not reproduce Pixelmon's full RGB-generation, cutout and scaling sequence.

| Retained case | Visible pixels | Recolored pixels | Recolored to black |
| --- | ---: | ---: | ---: |
| 80 px tunic | 1,898 | 293 | 92 |
| 80 px greathelm | 1,571 | 534 | 97 |
| Padded sword | 425 | 165 | 78 |
| Padded bow | 515 | 278 | 158 |
| All 59 views | 25,342 | 4,291 | 1,367 |

A control containing a connected brown 8 × 8 garment with a two-pixel gold buckle at (3,3) and (4,3) recolors both gold pixels from `(240,200,80)` to surrounding brown `(100,60,30)`. Item alpha is connected throughout. That is a known loss of an intended detail under the source's rule. The same mechanism can usefully remove a detached noise island, but color-island size alone cannot distinguish the two cases. Retain PixelDoll's native pixel grid and ownership-sensitive cleanup. A larger model render's quantization speckles and an already native one-pixel clasp require different evidence.

## Foundry's cutout and gates need their stated limits

The inspected green-screen remover removes strongly green pixels, then halves alpha for every remaining pixel with `G/(R+B+1) > 0.8`. The second condition has no edge-distance restriction despite the fringe comment. Equivalent controls on an otherwise green background leave yellow `(100,100,0)` and cyan `(0,100,100)` at alpha 127, while gray `(40,40,40)` and red `(150,40,20)` stay at alpha 255. The colors can occur in a solid interior region. This establishes a possible material-opacity change, rather than a measured failure rate on Foundry's generated roster. PixelDoll's production decoder would discard alpha 127, making this a particularly unsuitable drop-in preprocessing rule. [Cutout and crop functions](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/pipeline/foundry_gen.py) · [PixelDoll decoder policy](../../app/src/lib/items/run.ts)

The corner-transparency gate's result text expects at least three transparent corners, while the implemented condition fails only when three or more corners are opaque. A controlled RGBA image with corner alphas `[0,0,255,255]` consequently passes with only two transparent corners. Its alpha gate separately checks that the file mode is RGBA. These are mechanical format checks. Foundry requires later raw, pixel and finish review, and its exporter requires one finish-accepted winner in all eight directions. The source does not treat those mechanical checks as sufficient approval of a sprite. [Mechanical gates](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/foundry/mechanical.py) · [Accepted-winner export](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/foundry/cli.py)

Foundry's useful geometric precedent is its shared crop transform. It computes the bounding box from albedo once and applies that same crop and square-padding operation to corresponding normal and depth images. Separate auto-crops would misregister them. PixelDoll should apply that rule to future owner, material or depth labels with exactly the same recorded integer transform as their source pixels. Independently fitting each equipment frame would introduce motion and pivot changes, so the frozen body's existing coordinate system remains the experiment's frame of reference. [Shared crop implementation](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/pipeline/foundry_gen.py) · [Current coordinate and cut contract](../../app/src/lib/compose/compose.ts)

## Provenance and useful qualification rules

Foundry stores the accepted attempt per direction, checks every source file before copying it, hashes each emitted asset and records the recipe, seed, revision, rejected/regenerated counts and review times. Its manifest also contains the current export time, so repeated exports need not have identical manifest bytes. Content identity, ordering, review state and bitwise archive reproducibility are separate checks. PixelDoll's request hashes and retained receipts already support the same separation, including unknown outcomes that cannot be resent as recovery. [Export implementation](https://github.com/mcp-tool-shop-org/sprite-foundry/blob/9f0f3f75dce79d638f9ad2e6ae0b73cf015edaac/foundry/cli.py) · [Existing trial receipt validation](../../app/scripts/item-trial-report.ts)

Pixelmon's small-frame gate checks area against the standing reference and flags a bottom-contact case when the subject is much taller. Its retry path can paint up to three seeds and returns the first candidate if every attempt fails. Those source policies require adaptation to real-credit workflows. PixelDoll must preserve each failure and charge, and keep another generation attached to an explicit user request. A source author's local model retry loop provides no authorization to retry PixelLab automatically. The more useful test case is the original failure itself, retained alongside the best candidate and the exact reason a frame was rejected. [Frame gates and retries](https://github.com/grymmjack/pixelmon/blob/83a1678bde831d590d34704044099a524c8191de/sprites.py)

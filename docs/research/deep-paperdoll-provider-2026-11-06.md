# PixelLab generation and conditioning research

November 6, 2026. This audit checks the live REST schema, live MCP tool inventory, provider documentation, saved PixelDoll evidence, and the application routes that would use the findings. **Verified** means observed in the schema, protocol, code, or offline probe. **Documented** means the provider describes the behavior. **Hypothesis** means PixelDoll still needs a controlled comparison. No account assets were sent and no generations were purchased for this spike.

## Live provider audit

Fetched [REST v2 OpenAPI](https://api.pixellab.ai/v2/openapi.json) and compared it with the [October 20 snapshot](pixellab/pixellab-openapi-v2.json) and the [November 2 managed motion capture](pixellab/2026-11-02-managed-custom-v3-contract.json). Both full schemas expose the same 102 path names. The inspected raw skeleton, animation edit, transfer and inpaint request properties, descriptions and constraints match the October snapshot. The managed animation mode, frame count, directions and target-palette descriptions have evolved. Read the schema at its current URL rather than inferring the latest contract from the endpoint list or the older [capabilities review](pixellab/pixellab_current_capabilities_2026-10.md).

Live MCP discovery succeeded without credentials. On the documented [PixelLab MCP endpoint](https://api.pixellab.ai/mcp), send JSON-RPC `initialize` with protocol version `2025-03-26` and accept JSON plus SSE. Follow with `notifications/initialized` and `tools/list`, forwarding the session header if provided. PixelLab MCP Server 0.2.0 returned 107 tools. The [live assistant guide](https://api.pixellab.ai/mcp/docs) describes their semantics in more detail than the [product overview](https://www.pixellab.ai/mcp).

| Operation | Verified contract and provider behavior | PixelDoll consequence |
| --- | --- | --- |
| REST `edit-animation-v2` | `frames`, `description`, and `image_size` are required. Each frame is a PNG/JPEG base64 object with its own `size`. The usable frame caps are 16 at ≤64 px, 9 at 65–80 px, and 4 above 80 px. Two frames minimum. Optional seed, transparent background and target palette. An asynchronous receipt leads to edited composite frames. The live MCP `edit_image` has text or image-reference input and corresponds to `edit-images-v2`, a separate operation. | Main standing generation and anchored editing use REST. Anchored editing counts the reference among the frames edited, then ignores its generated output. An instruction to preserve the mannequin is a model request and needs local verification. |
| REST `transfer-outfit-v2`, MCP `transfer_outfit` | Separate `reference_image` and target `frames`, output size, optional seed, transparency, palette and up to 2,000 characters of transfer instructions. A reference consumes one grid slot, giving target caps of 15 at 32–64 px, 8 at 65–80 px, and 3 above 80 px. Two target frames minimum. Returns composites in target order. PixelLab recommends the same character in the reference because a different character can change very little or freeze the motion. MCP additionally accepts URLs, which are unnecessary for browser REST. | The production [shared-equipment fitting route](../../app/src/lib/equipment/generate.ts) already uses REST transfer for qualified cross-body standing headwear. Its [implementation plan](shared-equipment-fitted-copies-plan.md) documents the narrower supported range. Primary same-character animation uses [anchored edit](../../app/src/lib/items/run.ts). The unused same-character transfer case is a stronger provider match for a selected clip, with identical target capacity to an anchored edit. |
| REST `inpaint-v3`, MCP `inpaint_image` | White mask pixels can change, black should be preserved. REST requires `inpainting_image` and `mask_image` at the same size, 32–512 px canvas. `crop_to_mask` defaults to true. REST still mentions context and bounding box in its overview, but marks both properties deprecated. MCP takes a rectangle or image mask. The editor's black brush instruction describes its UI, not REST mask polarity. | The [grid builder and evaluator](../../app/src/lib/items/run.ts) keep the same-direction dressed reference black, enforce the exact submitted mask locally, and validate result geometry. The next experiment concerns mask construction and repair quality inside the editable area. A separate context input adds little evidence and uses a deprecated field. |
| REST and MCP raw Skeleton v3 | One PNG reference, its exact starting skeleton, and 3–15 target skeletons. Each skeleton has all 18 labeled joints, normalized x/y, optional `z_index`, and optional depth from 0–255. Omitted depth inherits the facing's standing template value. Provider says it redraws the reference first and learns the key and palette from that redraw. Results contain exactly one same-size frame per target pose and omit the internal reference redraw. The maximum dimension is 256 px. | [Item pose](../../app/src/lib/items/items.ts) and [body pose](../../app/src/lib/rig/clips.ts) share a request shape, but bare and dressed source rasters differ. Reusing frozen target joints is necessary for alignment. Whether the **source** joints still match a provider-redrawn dressed reference is a separate question. There is no raw Skeleton v3 field for a target palette, per-frame target raster, occlusion mask or item-only output. |
| REST `estimate-skeleton` | 0.1 generations per estimate. Padding is internal. Coordinates are normalized against the submitted canvas, including when the engine uses a larger power-of-two square. Fully transparent images are documented to fail before charging. Live MCP inventory has no standalone estimate tool. | An optional estimate can diagnose rest-pose mismatch on a dressed source. Joint positions inferred through gear require scrutiny, especially wrists, covered shoulders, helmet silhouettes and atypical proportions. Existing frozen target joints stay authoritative for the target sequence. |
| Managed Skeleton v3 | REST supports shared action-text motion through `animation_group_id` and describes 3–15 frames for custom text motion. Live MCP `animate_character` separately exposes `poses`, `scale`, `move` and `ai_freedom`. The last is documented as template-only. Managed pose objects and raw 18-joint lists are distinct schemas. | A managed render can supply coherent base motion across directions. It does not deliver interchangeable semantic gear layers. PixelDoll's [starter study](2026-11-02-eight-direction-starter-pack.md) and [motion contact experiments](2026-10-28-motion-targeted-authoring.md) qualify body output and timing independently from clothing. No reason to route production browser requests through MCP. |
| REST text v3 and PixMiniMax | Text v3 takes 4–16 even frames with total pixel budget 524,288. PixMiniMax takes 4–40 frames in multiples of four, returns the unchanged first frame before its generated frames, and accepts explicit facing, view, subject and initial-pose descriptions. Supplying all four with enhancement disabled avoids auto-caption rewriting. Both offer optional last-frame guidance. | Useful base-motion controls for allowed paths and research. A last-frame image can constrain endpoints but says nothing about intermediate silhouette, garment design or true looping. Running a dressed and an undressed text pass independently does not align them. |

The live inventory contains no semantic paper-doll generator. [Pro Flash masked inpaint](https://api.pixellab.ai/v2/openapi.json) is an adjacent capability with a changes-only output mode and documented outside-mask RGBA preservation. A changes mask can still contain body pixels and still needs semantic ownership checks. Pro Flash inpaint is outside this repository's allowed editor routes. MCP's separate `pixelart_workbench` exposes deterministic pixel operations and can author layered scenes. Its checks, region inspection and pixel patches with an expected old value are relevant interface precedents. Those facilities require a workbench image or drawing and are separate from automatic equipment extraction. Existing browser code can implement the same inspect, edit and recomposite pattern locally. ### Prices are dimensions and receipts, with some estimates

- **Documented by PixelLab.** The MCP inpaint guide says a 360 × 168 request bills 10 generations while 168 × 360 bills 15. Both canvases contain 60,480 pixels, so a formula based only on area cannot reproduce those examples. Plan eligibility is a separate constraint from price. Square 240 × 240 repair is a cleaner pilot for the recent compact-grid change. Preserve request orientation with the receipt in any cost study. There is no Inpaint v3 quote endpoint in the live REST schema. - **Documented, REST receipt unverified at the boundary.** MCP states raw skeleton cost of 2 generations at 3 frames, 3 at 4–14 and 4 at 15. REST provides examples at 3, 8 and 15. PixelDoll currently reserves 4 at 13–14. Its old live evidence verifies 3 for 12 frames. A 13- and 14-frame REST receipt with a genuine useful render can determine whether to reduce the conservative reserve. - **Verified defect in the starting implementation.** Shared equipment's full-fit plan uses `poseGensFor`, while its request builder had a separate limit table that reserves 4 above eight frames. Submission sums the request limits and rejects requests above the approved plan. A full fit with a 9–12-frame batch can therefore be offered for 3 generations and blocked against a 4-generation reserve before any API call. Use the shared estimator in the fit request builder and test quoted totals against constructed requests for 9, 12 and 16 frames. ## Prior research and external methods

The [November tool review](tool-review-2026-11-06.md) and its [generation](tool-spikes-2026-11-06-generation.md), [motion](tool-spikes-2026-11-06-motion.md), [layering](tool-spikes-2026-11-06-layering.md), and [chroma](tool-spikes-2026-11-06-chroma-and-occlusion.md) spikes show complementary limitations. Per-frame repair retains target motion but needs stronger item identity across calls. Whole-body clipping loses useful extensions. A translated standing image sometimes suffices for headwear, while a cape changes shape. Chroma classification alone can silently accept repainted body pixels as item foreground. The [October comparison](generation-pipeline-review-2026-10-25.md#182-posing-items-versus-dressing-the-real-frames) found more natural drape with direct dressing but larger design palette drift. Those experiments used different base methods, so the result does not resolve the route comparison.

Reviewed the sibling [Pip paper-doll spike](https://github.com/Shilo/pixellab-pip/blob/main/docs/pixellab/pixellab-paperdolling-research-spike.md), [operational guide](https://github.com/Shilo/pixellab-pip/blob/main/skills/pixellab-pip/references/paperdolling.md), [raw and managed Skeleton v3 study](https://github.com/Shilo/pixellab-pip/blob/main/docs/pixellab/pixellab-skeleton-v3-research-spike.md), and [REST/MCP parity](https://github.com/Shilo/pixellab-pip/blob/main/docs/pixellab/pixellab-mcp-vs-rest-route-parity.md). Pip's paper-doll extractor provides an independent registered-diff baseline. Its guidance limits body ownership claims to inspected output. Its old raw Skeleton v3 tests retain color and identity but show little gait or arm crossing on some motion inputs. One authored starting skeleton was 0.105 canvas widths away from the estimator at the median joint. That measures disagreement with an estimator, which has its own error, and does not explain every stiff clip.

## Offline reference conditioning probe

Replayed a previously accepted live shared-headwear fit from `spikes/api/out/shared-fit/one-view-move-test.pixeldoll.zip`, a local research cache. Read each raw dressed hash from `item.dressed` and each frozen body hash from `rig.rest`. Ran production `extractCell` with the standing head band, applied `toChroma` to the frozen body and recomposed the extracted layer with `recompose`. Counted changed RGBA at coordinates outside the extracted layer, plus alpha changes. The candidate is a new reference raster for comparison only. It uses the same position and dimensions as the stored rest.

| Facing | Raw redraw RGBA differences outside item | Of those, alpha differences | Rebuilt reference differences outside item | Item pixels retained |
| --- | ---: | ---: | ---: | ---: |
| South | 498 | 0 | 0 | 107 |
| East | 297 | 0 | 0 | 103 |
| North | 464 | 0 | 0 | 132 |
| West | 296 | 0 | 0 | 104 |

The raw reference changed every visible non-item pixel's color on these four views, while its non-item silhouette stayed aligned. Rebuilding establishes exact input color identity outside the extracted layer and leaves the isolated helmet raster unchanged. It may improve how Skeleton v3 learns the key from the starting redraw. This case offers no evidence of a geometry correction or a better generated clip. Restrict a pilot to reviewed rigid headwear with no cut, no rear layer and no disputed mask. A raw render can encode occluded shoulders, rear drape or other information a simple over-composite would lose.

## Ranked experiments and acceptance

1. **Separate reference conditioning from target pose ownership.** Start with the accepted 64 px helmet and a walking side view, plus a second wearer and a strongly occluded attack. Compare raw dressed start versus rebuilt keyed start, with identical requested joints, action text, seed, view, canvas and target count. Freeze the same source item artwork. If the raw resting image and its source joints demonstrably disagree, add a distinct arm with a verified source-only adjustment. Reuse the same frozen target sequence throughout. Use at least three paired seeds on promoted cases and preserve the worst sample, not just the best. Compare key loss, newly keyed background, grip/occlusion, item silhouette, item palette distance, actual frame count, latency and usage. A source normalization that washes away cut or back-layer information fails.
2. **Compare true outfit transfer against anchored edit and pose on the same frozen frames.** Reuse the accepted reference for all arms. Start with an eight-frame 64 or 80 px walk and two or more frames of a crossed-arm or prone pose. Use one worn garment with sleeves and one cape. Send the same target PNGs and chroma key to both editor arms. Match the semantic instructions, with one route-specific difference for how each identifies its reference. For transfer, state the target facing and explicitly preserve exposed skin and original pose. Above 80 px, compare chunks of three target frames so both editor arms get equal context. Include the approved same-facing reference for every chunk. Score blank/repeated frames, garment consistency, occlusion, exact body composition outside allowed edits, and cost per accepted result. Test standing-reference versus nearest useful vetted pose only after determining the better route. Keep the pose default if transfer's fit gain does not justify its higher cost or causes cross-frame design drift.
3. **Constrain colors only after the design exists.** REST edit and transfer accept explicit hexadecimal colors and optional `max_colors` of 2–64. A cap alone may choose a different palette across requests. In transfer an explicit palette sets final colors even when the reference contains different RGB values. Test a union of all key shades required by the batch and the accepted item's dark outline, highlights and material ramps against no constraint. Pair the same request and seed. Measure exact keyed-body color survival, color collisions against the key scorer, and gear detail retention. Preserve unpaletted control outputs. Reject any palette that steals cyan or green material, merges outline steps or forces foreground shading into the body key. This applies only to edit and transfer, since raw Skeleton v3 and Inpaint v3 expose no target palette.
4. **Prototype bounded repair masks and repair receipts.** Compare the current band, a confidence-qualified pose-warp mask, and a body-part-protected mask on exact retained or synthetic pixel truth before spending. A narrow mask built from an already missing sleeve must fail qualification. Then compare masks on one small localized issue and one partial/empty garment with known adjacent support. Keep all nonselected cells and views byte-exact. Where a mask is authoritative, any extracted or cut pixel outside it is a deterministic failure. Record both RGB and alpha changes inside and outside the mask and which pixels were clipped by local extraction. Compare the 240 × 240 square repair with its prior geometry only if both routes are otherwise comparable and qualified. Use the actual receipt for cost.
5. **Track a broader scorecard before expanding automatic acceptance.** Include headwear, eyes/hair conflict, torso with raised arms, pale skin versus leather, cloak behind body, boots, two held lengths, front and side, north and mirrored west, a 64 and 80 px body, and one larger padded held case. Keep one easy walk and one non-looping action per candidate category. Mark true transparent cells and legitimate occlusion separately from missing output. Report accepted cells and complete accepted clips per paid unit as well as per-arm QA counts. Review every native frame and a slowed playback with the same frozen body. An unchanged anchor hash and a passing chroma count alone do not guarantee the equipment looks right.

For all experiments, preserve the sanitized request hash, route version, ordered target and reference hashes, dimensions, orientation, seed, provider-reported usage, request-to-ready time and post-processing decisions. An identical seed is a paired control and does not guarantee repeatable pixels across a provider update. Submit deliberate paid arms once and reuse retained job results for offline comparisons. Structural corruption, unauthorized body edits, wrong frame counts and unexpected dimensions remain hard failures even if average visual scores improve.

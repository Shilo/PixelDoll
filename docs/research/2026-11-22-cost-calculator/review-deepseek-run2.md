## Worked example 3 (98.65)

Recomputed from the code at 128 px, 4 independent facings:

- Base: V3 text draw `ceil(8*128^2/65536)=2`, plus text 1, plus registration 0.25 = **3.25**.
- Text V3 Idle, 4 frames: `ceil(128*128*4/65536)=1` plus 0.4 checks = 1.4 per facing, x4 = **5.6**.
- PixMiniMax Attack, 12 frames: table 128 at index `12/4-1=2` is 2, plus 1.2 checks = 3.2 per facing, x4 = **12.8**.
- Hair: one dress call at 128 = 10 (cap 9 holds 4 facings); poses 4 and 12 frames = 3+3 per facing, x4 = 24; total **34**.
- Referenced held item: cell 128+2*16=160, cap 4, reference reserves one slot, so 3 then 1 = 2 calls x 15 = 30; Attack poses 12 frames = 3 per facing, x4 = 12; total **42**.
- Pixen State: one 2x2 packed sheet = **1**.
- Sum: 3.25 + 5.6 + 12.8 + 34 + 42 + 1 = **98.65**. The 99.05 ceiling adds 0.4 for four missing rest checks.

The held subtotal of 42 depends on the uploaded reference. Without it the first held call would hold all 4 facings, one 15-gen call, and the example would be 83.65.

The repair note is wrong in one dimension. `repairGridPlan` defaults to the 512 side, so the grid is **512x256** (mean 384), not 384x256, and costs 15 at Tier 2. Tier 1 splits into 3+1 cells at 256, two batches for 20. The 15 and 20 values are right.

The prose at line 134 conflicts with itself: 2,271.25 plus the walk preset at 5 views is 2,281.25, but that ignores the 135 saving that just produced 2,136.25. If both changes apply the total is 2,146.25.

## What a calculator must also count

- **Standing clips do not multiply dress calls.** `standingCoverage` can include several one-frame clips (`studio/itemRoute.ts:88-117`), but `planItem` dresses one rest key per independent direction (`lib/items/items.ts:661-665`) and the result is reused for every matching standing clip (`lib/items/run.ts:1198-1204`). Line 55's "coverage per eligible clip and facing" overcounts standing coverage; only moving clips multiply.
- **Body palette repair item reposes.** A reviewed palette repair adds `poseGens(items, frames, facings)` = `items x facings x sum(P(batches))` (`studio/create.ts:2035-2039`; `lib/items/run.ts:1783`). The spec names the reposes but gives no count.
- **Managed State is one request for the whole parent, not one per facing.** The preamble's "one new still body cell per available independent facing" must not become a per-facing 10/15/25 charge. Route eligibility also needs Pro, a character id, description <=1000 characters, no reference, and parent size equal to the cell (`studio/stateGeneration.ts:302-320`; `studio/stateGenerationPlan.ts:249-265`).
- **Enhancements are outside every planner.** Character, item, motion, and pose enhances are foreground paid calls and are never included in `estimate`, `moveEstimate`, `planItem`, or `planStateGeneration` (`studio/promptEnhance.ts:62-136`). The calculator must count each call separately, not only mark the price unknown.
- **Repair side is a choice, not always 256.** The default limit is 512; 256 applies only with `preferTierOne` (`lib/items/items.ts:309`). Show both generation counts and tiers, since Tier 1 can cost more.
- **Held padding is skeleton-only.** Anchored held items use the unpadded rig cell (`lib/items/items.ts:427-436`), so the item method must be an input; assuming 96/160 px for every held item overprices the anchor route.

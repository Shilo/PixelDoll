# State authoring in PixelDoll

Use **Pose** for a reusable still of the same paper-doll body. A pose has one frame per supported facing. A move can use that pose as its starting reference and save its own body frames, fitted item frames and timeline. Keep the reference decision in authoring. The same playback API can display both.

PixelLab Character Creator calls full alternate character versions **states**. Those versions can change appearance and each owns a separate animation list. PixelDoll should accept compatible PixelLab states as reusable poses, and offer import as a separate character when a state represents a different body. An outfit assembled from swappable items remains an Outfit. [Character Creator research](../2026-11-18-character-creator-states.md)

Static **Ride** remains a one-cell move when authored in that format. Riding is a gameplay role selected by the mounted resolver. A reusable pose is a user-assigned source role. Do not infer that role from frame count, the word “Ride,” or the provider's asset category. Future **Save frame as pose** can make a named reference from an approved move cell through the same import and geometry checks.

For ZIPs with different looks, show a body and pose comparison. Ask the importer to identify baked-in gear or a changed body. Offer a separate character with its selected imported moves and explain that the current project's wardrobe, outfits and color choices stay with the current project. Gear already baked into the source remains part of its artwork. For the same body, use PixelDoll's wardrobe when equipment needs to stay swappable. A geometry pass alone cannot establish the same look.

## Asset data and the display API

- Publish each ready pose as an ordinary one-cell clip with a stable, opaque ID on the same cell grid, pivot and camera as moves. Treat the source role and human label as explicit metadata. A displayable move can also have one cell. Pose IDs and labels must never affect selection of `walk`, `idle` or `ride`.
- Retain the exact frozen source that an authoring operation needs, per direction: image hash and geometry, normalized placement and pivot, source joints and appearance description, optional provider origin, and source revision ID. A named pose can point to its latest revision. Moves carry the revision used for generation and own their rendered body cells and item cells. Keep the standing keyframe used by dressed equipment independent of the selected body source.
- Use the existing display API. A host finds a clip by ID, calls `sampleTimeline` with its frame list, elapsed time and loop policy, then passes that clip ID, facing and sampled cell to `drawList` or `composeCell`. Studio consumes the same behavior, and exported adapters keep their `play` equivalents. Keep stage-specific facing fallback and mounted movement policy outside the portable compositor.
- On new imports, check decoded size, pixel placement, required directions, mirror intent, camera, identity and crop. Pose and standing art can differ, so visual review is necessary to detect a changed body or baked gear. Do not recenter existing artwork to accommodate an oversized sibling. The first slice imports those siblings as separate projects or leaves them out.

Store the Pose role, editable names and source revisions in editable project metadata keyed by clip ID, outside `RigAnimation`. Existing manifest provenance is a separate field and already travels in exports. The portable playback contract continues to use the stable ID, available directions and timeline. Rename changes the source label without changing the exported ID. Keep the first playable clip stable when adding poses, because several adapters pick their startup clip by order. Append new pose IDs and order the Studio panels independently. Derive equivalent facing availability from editable base cells and exported sheet metadata at their existing boundaries. A pose with no joints can be exported when its display artwork validates. Use the existing clip selection for excluding it from an export.

Readiness is per operation and facing. Preview can show imported cells before pose setup. This must leave existing moves and Standing fit workflows usable even where today's rig readiness checks every populated clip for joints. Raw authoring needs exact pixels, placement and verified joints for all requested facings, and managed generation additionally needs a matching accessible provider reference. Report missing art in Preview and never treat reflected views as individually authored. Independently drawn art needs a facing the rig can represent.

The runtime probe holds a distinct still and plays a two-cell move with a separate gear layer through `sampleTimeline` and `composeCell`, including a mirrored facing. The existing `retainMoves` helper prunes the source pose and rebinds retained items. Even with the pose body blob removed from memory, the move's composed pixels and Generic move strips are byte-identical. This proves playback independence and tests manifest pruning. It does not exercise IndexedDB deletion or revision recovery. [Playback probe](playback.test.mts) · [Runtime contract](../../architecture/javascript-runtime.md)

## PixelLab endpoints and job lifecycle

| Operation                                     | Request and publication plan                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Import a pose from a local file               | Decode selected ZIP rotations or explicitly mapped directional images. Validate and stage using the existing immutable grid, then publish the local art without PixelLab. Use matching, validated joints when supplied. Offer explicit joint setup where needed before the pose can be used as a source.                                                                                                                 |
| Create a provider state                       | For a supported four- or eight-direction parent, review the edit and price, then submit `POST /create-character-state`. Persist child ID and job ID. Poll the job and fetch the child through `GET /characters/{character_id}`. A completed job can be a receipt without image payloads. Publish only after validating the full child snapshot. Qualify billing, access and receipt behavior live before release.        |
| Create a local pose without a provider parent | A stored-frame capture or directional art import stays local. For generation, compare the allowed image-conditioned edit and skeleton paths with real art first. The current humanoid skeleton route needs at least three targets even if one result is saved. A provider state ID is an account resource, so it cannot be inferred from a local pose.                                                                   |
| Generate an authored move using a local pose  | Build authored targets using that revision's matching-facing joints. Send the exact frozen image and joints as the reference to raw `animate-with-skeleton-v3`. Measure and validate results before staging. Split local rig readiness from the managed account character requirement so this route can use a measured local pose.                                                                                       |
| Generate a described move                     | The current managed `/characters/animations` path can source motion from its registered character. With an alternate local pose, first qualify an allowed image-conditioned route or a documented direction-specific starting-frame override. A provider ID alone is insufficient to prove it still represents the pinned local art. Avoid selecting a different source automatically when permissions or pixels change. |
| Save fitted gear                              | Pair a dressed keyframe with the joints for that exact keyframe, and fit it against the move's validated target poses. Existing dressing comes from Standing. Never silently substitute alternate-pose joints for Standing joints, or reuse a standing item just because a clip has one cell. Show uncovered equipment and the cost of fitting it before submission.                                                     |

Use the existing client-side queue and transactional project publication. Freeze source revision, requested facings, expected results, route, tier and estimate, seed, and target move version in the approved plan. Persist request identities and known job IDs, poll those IDs on reload and stage validated results. A lost submission receipt requires review without an automatic resend. Cancellation releases the local draft or records the provider outcome and usage. Publish body cells, source metadata and the operation receipt together after checking source and target identity. Fit gear as a separately recoverable operation if it cannot commit with the body. Resume known work from saved artifacts and present new spend separately.

Managed state generation needs to recognize completed receipts without images. Recover metadata-only completion and an expired job with a known child by checking the child resource before any retry decision. Keep a partial download unpublished. Reconcile cancellation conflicts and credential changes with the known job, never by submitting a replacement. For alternate-source gear, build the source from the exact dressed image and its own padded source joints. The current pose route uses the move's requested target joints and stores measured joints separately for QA. Prove registration and attainment against the actual body before reusing that policy for newly supported sources. An uncovered item remains uncovered, and a late fit must match both the item and the body revision.

Removing a pose is a local transaction. A still-running operation must either keep an explicit pinned snapshot through completion or be cancelled/blocked by policy. The initial implementation should block removal while it is the source of an active operation. Retain revisions referenced by saved moves or pending work through garbage collection and editable ZIP export. The published renderer must continue to work even if the remote resource or source revision is unavailable. Remote deletion is outside this local flow because PixelLab deletes the provider state and its animation list. [Public API](https://api.pixellab.ai/v2/openapi.json) · [Queue](../../../app/src/lib/pixellab/queue.ts) · [Project transactions](../../../app/src/lib/store/db.ts)

Editable full-character and move-only ZIPs should carry authoring revisions needed by included moves, including retired ones. An existing PNG entry alone is insufficient because the loader, archive reader and subset builders each choose which hashes to keep. Keep operational queue receipts local so an imported ZIP cannot resume paid work. Missing or altered source art can disable regeneration while preserving valid published frames. Prove both orders of the cross-tab race between registering new work and removing its source. Rebind only items tied to the previous base hash and preserve their unaffected coverage.

## Release order and verification

1. **Local import, preview and removal.** Test grouped ZIPs with compatible and incompatible siblings, duplicate names, missing and mirrored facings, and changed artwork. Preserve standing art, pivot, existing gear pixels and move cells. Recompute the base hash and rebind matching items atomically as existing Add a move does. Verify no-key local use, editable full and subset ZIP round-trips, delete races, export startup selection and included-engine compatibility before exposing the first pose clips.
2. **Source selection for an authored body move.** With two visually distinct fixture poses, verify that preview selection leaves Standing as the default. Capture the request for an explicitly selected pose, its matching joints, generated directions and unchanged mirror mapping. Test lost responses, duplicate completion, source replacement or retirement, and stale target conflicts. Remove the source after saving, then reload and verify the same saved clip and frame bytes.
3. **Gear, engine and live qualification.** Capture a bounded side and diagonal authoring trial using a correctly dressed reference and visible equipment. Verify billed receipts, source and target hashes, alignment and separate item coverage. Test the exact same pose ID through Studio and Generic, Aseprite, Phaser, GDevelop, Godot and Unity. Native success requires the existing engine harnesses, not only export file generation. RPG Maker's walking-sheet exporters need an eligible gait selector and explicit excluded-clip feedback. The probe confirmed that today's first walk-like ID can select a still ahead of `walk`.
4. **Provider generation and described motion.** Qualify supported direction counts, result URLs, cancellation, API account restrictions and post-job snapshot behavior with real receipts. Verify every stage with separate body and fit costs. Keep price and route proposals provisional until that evidence exists.

## Research evidence

- The existing `character-import` test file passed all 105 cases. This covers current imports and does not imply that PixelDoll stores additional poses today.
- The isolated playback probe runs against PixelDoll's actual runtime and Generic exporter using synthetic art. It also reproduces the gait-ID collision and shows that growing the canvas changes existing pixel placement.
- The interactive layout uses PixelDoll sample art and Bronze controls. Browser checks at 320, 844 and 1000 px covered grouped selection, pause, mirrored facing, unfitted gear, both source entry points, removal with retention disclosure, and disabling a preview-only source. Dark and light were checked. The sample forms use in-memory records and stand in for decoding, persistence and generation.
- The research used the public specification and offline fixtures. No PixelLab generation or native import was performed for this spike.

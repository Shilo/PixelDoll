## Confirmed defects corrected

1. **Memory-only credentials were broadcast to every listener on the origin.** The queue previously sent a follower-entered key via `BroadcastChannel`. Removing only an ask-for-key responder had left passive interception possible. The channel now carries ledger notifications and a credential-free Forget signal. Typed/replacement credentials stay in their own tab; old/malicious key messages are ignored. Connect/Activity copy explains which tab must be connected.
2. **Late balance responses could restore forgotten account information or reject a replacement key.** A credential revision now discards old success/error responses, including Forget followed by reconnecting the same key. Cross-tab Forget also clears remembered/account display state.
3. **Disconnected followers could later acquire the queue lock and restart work.** Pending lock requests are aborted and callbacks are guarded. Obsolete async flows cannot enqueue after disconnect or carry an unfinished enqueue across reconnection; never-connected isolated test queues remain usable. A disconnect during asynchronous ledger loading cannot restart the timer. Suspended ticks recheck their connection identity after balance probes and ledger merges, so releasing the lock prevents those continuations from submitting work. The [Web Locks specification](https://w3c.github.io/web-locks/#api-lock-manager-request) forbids combining `signal` with `ifAvailable`: an initial implementation accidentally did so; the parent caught this in Codex browser, it was corrected immediately, and the fake lock now enforces that browser restriction. Only the blocking request uses a signal.
4. **Pose adherence silently omitted missing frames/joints from its average.** Complete good observations could hide missing failed observations. Missing/nonfinite requested measurements now fail with an explicit incomplete-measurements message. Joint validation rejects duplicate, conflicting, unknown and nonfinite observations.
5. **Malformed inpaint grids could be sliced using an incompatible layout.** Divisibility by a cell size was insufficient: a two-column result could be interpreted as four columns, wrapping rows or reading absent pixels. Draft and accepted-item grid paths now require exact submitted dimensions, including reference cells. The pure cutter also rejects incompatible width, truncated rows and fractional row heights before slicing.

6. **Automatic creation resumption could issue a paid request again after an unknown terminal outcome.** Live Codex browser testing caught a lost rest-import record followed by a second paid submission during HMR recovery. `Queue.enqueue` now defaults paid POSTs to resume-safe behavior; explicit rerolls change the seed. Matching newer active/successful records are selected ahead of historical failures. Parent also made the orchestration default explicit and Studio agent added entry guards and a full reload boundary for dev state HMR.

7. **Failed parallel direction branches kept progressing and spending.** Live evidence showed a rejected create batch while siblings continued estimates/rerolls and wrote progress into a later explicit attempt. Creation and move batches now own a shared cancellation scope. First failure blocks subsequent paid work, including requests whose blob/hash preparation was suspended. Only waiting work is canceled; already sent HTTP continues under queue ownership. The final submit boundary checks lifecycle and ephemeral per-record scope after persistence/image rehydration, immediately before HTTP. Canceled preflight is distinguished from an unknown network outcome. Cached active records attach to every live consumer scope. One failed scope cannot cancel a shared request required by another scope or a live unscoped caller. Automatic pre-submit cancellations record all participating attempt seeds; a deliberate distinct attempt may recover those unsent requests, while same-attempt reloads, user cancellations and lost/sent outcomes remain blocked. Studio state revisions independently suppress old progress callbacks.
8. **Displayed creation credit ranges omitted configured retries.** The old +30% range was below the possible second render of every clip-direction. The estimator now shares `CLIP_ATTEMPTS` with rendering and includes all clip rerenders plus possible rest-joint fallback: baseline/max estimates35.25/57.15 for four views and57.25/93.75 for eight. UI rounds these to35–60 and57–95 and explicitly labels cost/time as estimates; this is not a guaranteed account spending cap.

Paid POST uncertainty handling now applies across submission and automatic orchestration recovery: unknown network/server outcomes are not resent. New queue tests exercise a keyless leader, a privately connected follower, leader closure and exactly one submission using the follower's own key. Existing running records continue polling rather than being resubmitted.

## Synchronous estimate timeout follow-up

The parent's second live create exposed `estimate-skeleton` requests lost at the app's120second HTTP cutoff. This is separate from background animation polling. The current [OpenAPI](https://api.pixellab.ai/v2/openapi.json) exposes only synchronous `POST /estimate-skeleton`, taking an image and returning joints; there is no documented async estimator/job-ID alternative or duration SLA. The official [Python estimator](https://raw.githubusercontent.com/pixellab-code/pixellab-python/master/pixellab/estimate_skeleton.py) calls `requests.post` without a timeout; the [JavaScript estimator](https://raw.githubusercontent.com/pixellab-code/pixellab-js/master/src/api/estimateSkeleton.ts) uses its [fetch wrapper](https://raw.githubusercontent.com/pixellab-code/pixellab-js/master/src/utils/fetch.ts) without a deadline. Those SDK clients default to the older v1 base, so they are transport context rather than a v2 service guarantee.

The app now allows a bounded ten minutes for the synchronous estimator and retains two minutes for asynchronous job submission/free reads. This is an inference from the synchronous contract and observed slow-service behavior, not a proven provider SLA or availability fix. Existing lost requests stay terminal and are not resent. Five mocked HTTP-boundary tests verify timeout selection and one fetch per request without spending credits. No new paid requests were issued by this research lane.

## Can managed poses avoid redundant import setup estimates?

Read-only follow-up after the parent recovered its live v3 character, 2026-10-22. No paid requests and no source changes were made for this investigation.

The current [OpenAPI](https://api.pixellab.ai/v2/openapi.json) distinguishes two potential sources:

- `GET /characters/{character_id}` returns `CharacterDetail.skeletons` as an untyped object. Its description says rotations are stored by direction and animation data lives in the internal `character_animations` table. The established application/spike shape is `skeletons.2d_references[direction].keypoints`; S3 measured those rest coordinates within 0.11 px of separately estimated rotation joints.
- `AnimationGroup.directions[]` references `AnimationDirection`, whose only properties are `direction`, `frame_count`, and frame-image URLs. There is no documented GET route for an individual animation's skeleton sequence. The create-animation operation and deletion routes do not provide a read-only pose retrieval alternative.
- The public ZIP operation's prose claims metadata includes skeletons for all frames, then qualifies its keypoint description to template-based characters. Its metadata response is not typed, so prose cannot establish presence or coordinate layout for current v3 characters.

Actual evidence challenges the ZIP prose: fetched the parent's already-created character `0fffe6e5-4698-4074-8d38-fd2da03bb501` through the public, unauthenticated `GET /characters/{id}/zip?states={id}`. It returned HTTP200 and 47,641 bytes containing 29 files: 28 PNGs and metadata. `metadata.json` contained `group_id`, one `states[]` record (`character`, `folder`, `frames.rotations`, `frames.animations`), export version and date. It mapped four rotations and three sparse eight-frame walking directions. A recursive search across the entire metadata found **zero** fields matching keypoint, skeleton or joint. This v3 ZIP cannot replace the 28 unique-frame measurements needed by setup. The provider's old template-specific ZIP promise must not be treated as evidence of current v3 animation pose availability.

A bounded future optimization is still justified for exact rest images. Preserve source state/character identity during PixelLab import (currently `pixelLab()` returns `extra: {}` and discards that registration). For an owned managed character, obtain its existing rest joints with a free authenticated character GET. Require all 18 known finite normalized joints. Fetch the corresponding public rotation and apply the exact import normalization, then require its image hash to equal the selected standing reference hash before attaching the joints. A name, direction, or UUID alone is insufficient: users may choose another rest clip, change frames, or import another state. Transform coordinates using source canvas dimensions and the normalization offset (`x64 = (xNormalized * sourceWidth + offsetX) / 64`, similarly for y; a 48px source is offset by +8,+12). Reject or fall back when normalized joints fall outside the valid cell; never silently clamp or use template target poses as measurements of generated pixels.

This would save up to four/eight rest estimates where exact registration can be proven. It does not remove animation-frame estimation from the demonstrated v3 import. Preserving future ZIP keypoints should wait for an actual payload fixture with verified source dimensions, labels and frame mapping. The untyped character skeleton object could theoretically contain undocumented data; without an authenticated response proving that shape, public-schema absence is not proof of server-internal absence. No speculative pose reuse was implemented during the active paid validation.

## Creation publication identity and overwrite prevention

A final challenge found an existing publication defect: a completed create used `rig-<body-hash-prefix>` as its project key and unconditionally put the new manifest there. Recreating cached identical body pixels could therefore erase the existing project's equipment, recolours, outfits or direction policy. Body similarity is not project identity.

Creation now assigns a UUID project identity to its pending specification before any paid work. Previously pending specifications without an identity migrate once and are persisted before resuming; a duplicate legacy recovery is safer than overwriting a customized saved project. A fresh explicit retry receives a fresh identity. The internal `StoredProject.creationSpec` fingerprint identifies the original creation intent separately from its mutable manifest and is excluded from engine/editable export identity.

Before queueing anything, creation checks its saved identity. A matching already-published attempt returns the current saved project unchanged, even after its name, body moves, equipment or outfits have changed. Reusing an identity with a different seed, name, description or direction policy fails before paid work. Completed character pixels and metadata publish through the existing insert-only `putCharacter()` transaction, which uses IndexedDB `add` and writes blobs in that same transaction. If concurrent completion loses the insertion race, it may reuse only the matching published attempt; it never puts over the winner. Storage failure cannot falsely report successful publication.

Regressions cover customized post-completion recovery with changed body hash, four mismatched-intent cases with zero enqueue calls, independent new identities for identical body hashes, concurrent insertion preserving the winner and equipment accepted during completion, atomic image publication/quota failure, and pending identity persistence before the creation runner starts. The30test publication/state/policy/generation subset and strict Svelte/TypeScript checks passed; the data/export lane independently counter-reviewed the marker, insertion race and export/clone exclusion.

## Measured-pose boundary and selection

Managed standing references and raw estimator responses are now validated **before** four-decimal rounding or reordering. A just-outside coordinate such as 1.00004 cannot become an apparently valid 1; duplicate/unknown/extra raw labels cannot disappear through label lookup. The pipeline accepts exactly 18 known, unique, finite, normalized joints. The provider estimator output schema itself only promises numeric coordinates; normalized 0–1 is the consuming raw-v3 request contract and established measured evidence, not an invented guarantee about every provider output.

All supplied non-null standing coordinate maps are preflighted before any missing-view estimate or animation call. Incomplete or malformed maps fail with the direction named, retaining already-created artifacts. Nullish skeleton/reference/view/keypoint containers remain unavailable and use the existing bounded estimate fallback. The primary character schema explicitly permits `skeletons:null`; extending unavailable semantics to its untyped nested containers is a compatibility inference. Null/string/nonfinite actual joint coordinates remain malformed.

A further adversarial case showed that counting missing measurements as an ordinary QA failure still allowed `renderClip` to select and publish incomplete pose data after its bounded retries. Only candidates with exact complete valid measurements can now enter best-candidate selection. A complete clip with palette/border/adherence warnings remains reviewable and can beat an incomplete candidate with fewer scalar flags. If every attempt lacks measurements, creation/body replacement fails before publication; an earlier complete warning candidate survives a later incomplete reroll. This enforces the new-render boundary without retroactively invalidating historical projects that lack measurement metadata.

Focused regressions exercise deferred old-credential submit/poll/probe errors, accepted-ID contradictions and reload retention, nullish managed fallback versus malformed supplied joints, rounding and label adversaries, and actual `addMove` replacement using real synthetic PNG encoding/decoding. The latter proves two incomplete attempts perform zero cell/project writes, and complete art-warning candidates win in either attempt order. No paid requests were issued by this lane.
